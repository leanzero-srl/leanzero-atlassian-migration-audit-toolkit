# LeanZero Atlassian Migration Audit Toolkit

Three read-only Node.js tools that answer the question every migration eventually has to answer out
loud: **did everything actually arrive?**

Apache-2.0. Nothing in this repository writes to Jira. Every tool reads two instances and produces a
spreadsheet.

---

## The problem this exists for

A migration report tells you what the migration *believes* it did. It is generated by the same
process that did the work, from the same assumptions, and it is therefore the one source that cannot
independently confirm anything.

The questions that matter are asked from outside:

- Which issues exist on Data Center and **do not** exist on Cloud?
- Which Data Center custom fields have **no** Cloud counterpart — and why not?
- Do the two instances actually agree on issue types, link types, priorities, hierarchy and sprint
  configuration, or only look like they do?

These three tools answer those, in a form you can hand to a client.

---

## What is in the box

| Tool | Answers |
|---|---|
| [`find_missing_issues`](./find_missing_issues) | *Which work items are on DC and missing from Cloud?* Compares by issue key across both instances and produces an `.xlsx` with one tab per affected project plus a summary. Handles label-based key remapping, for issues that had to be recreated under a new key. |
| [`dc_cloud_field_report`](./dc_cloud_field_report) | *Which DC custom fields exist on Cloud, and why don't the rest?* Matches by name and emits a two-sheet workbook — the DC→Cloud field map, and the DC fields with no Cloud equivalent, each with a reason. Run it **before** the migration to predict what will not map, and after to confirm what did not. |
| [`jira_config_comparator`](./jira_config_comparator) | *Do source and target agree?* Compares issue types, issue type schemes, issue link types, priority schemes, priorities, issue hierarchy, sprint/board configuration and time-tracking settings between two Cloud instances, and reports every difference. |

## Start here

```bash
git clone https://github.com/leanzero-srl/leanzero-atlassian-migration-audit-toolkit.git
cd leanzero-atlassian-migration-audit-toolkit/find_missing_issues
npm install
cp .env.example .env
node main/find_missing_issues.js
```

`.env` is shared across all three:

```bash
DC_BASE_URL=https://jira-dc.example.com
DC_PAT=your-personal-access-token          # or DC_USERNAME + DC_PASSWORD
CLOUD_BASE_URL=https://your-site.atlassian.net
CLOUD_API_TOKEN=base64-of-email-colon-apitoken
```

## Things that will bite you, and what to do about them

**Freeze the source, or re-run the scan.** If Data Center is still live, every checkpoint is stale the
moment it is written and the "missing" list grows for reasons that have nothing to do with the
migration. Lock DC read-only first (see the
[admin toolkit](https://github.com/leanzero-srl/leanzero-jira-admin-toolkit)), or discard old
checkpoints and scan fresh.

**Cloud paging is the bottleneck.** Data Center happily returns 1,000 issues per page. Cloud's
`/search/jql` caps at 100. On a large corpus that ratio, not the network, is what sets the runtime.
Plan for it; do not "optimise" it by lowering the DC page size to match.

**An empty result is not proof of absence.** If your account cannot see a project's issues — a
permission scheme, an issue security level, a missing role grant — the audit reports zero and looks
like good news. Before you believe any zero, prove your credentials can see that project's issues at
all. On that project, not a different one.

**Field name matching has false twins.** Two fields called `Segment`, one of them a
`(migrated)`-suffixed duplicate, are not the same field. The report shows both; it is your job to
decide, not the tool's to guess.
